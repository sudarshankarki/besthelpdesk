5. New Request and Service Ticket Workflow

  1. User opens New Ticket and sees the New Request chooser.
  2. General Support keeps the user on the standard ticket form, defaulting to Service Request.
  3. The form validates department, branch, assignment email, notify email, CC emails, impact, urgency, and attachments.
  4. On submit, a Ticket is created with a generated ticket ID and calculated priority.
  5. Assignment and notification emails are sent based on assign/notify/CC fields.
  6. Assigned users, department users, requester, and support users see the ticket according to permission rules.

Assignment is tracked on the ticket and in assignment logs. Department-only tickets can be claimed by eligible department users. CBS tickets use the concerned CBS access provider label for the assignee once the request reaches the post-approval stage.

7. CBS Access Request Workflow

  1. User chooses CBS Access, then Head Office or Branch.
  2. The CBS form records user information, access-user acknowledgement, type of user, old user ID, user groups, amendment reason, endorsement, after-approval assignee, CC users, and digital sign-off chain.
  3. The system creates a CBS ticket and linked RemoteAccessApproval record with CBS-specific request type.
  4. The first pending reviewer receives an email and in-app notification.
  5. For branch requests, the second recommender is used only when selected.
  6. Final approver can approve or reject. Rejected requests can be corrected and resubmitted by the requester before finalization.
  7. On approval, signature snapshots and request data generate the approved CBS document.
  8. The ticket is assigned to the selected concerned CBS access provider and copied to after-approval CC users.
  9. Central Operation can download the CBS Access Report CSV from the CBS Access Requests page.

8. Remote Access Approval Workflow

  1. User opens the remote access request form from New Request.
  2. The form captures request details, recommender if selected, and final approver.
  3. A ticket and RemoteAccessApproval chain are created.
  4. Reviewer actions move the request from pending recommendation to pending approval or directly to final decision.
  5. Approval or rejection is saved with actor, note, timestamp, notification, and visible ticket state.

9. Incident Ticket and Incident Report Workflow

  1. Incident ticket intake captures incident-specific data and identifies the owner/commander.
  2. Incident report page creates or edits a structured IncidentReport.
  3. Evidence attachments are linked to the incident report and shown to permitted users.
  4. Registered user signs the registered section from their uploaded profile signature.
  5. Notified signers sign in configured order; earlier levels are reviewers and the final level is acknowledgement.
  6. If a signer requests correction, later signatures are cleared and the report becomes editable again.
  7. When all required signatures are complete, submit sends the report, locks editing, and marks the linked ticket resolved.

11. Notifications, Email, and Documents

  • New ticket email goes to notify email or default support mailbox, with CC emails when provided.
  • Assignment email goes to a specific assigned user when set.
  • CBS approval flow emails the next reviewer, then requester, then concerned CBS access provider after final approval.
  • After-approval CBS CC users are copied on the approved assignment email and appear as normal comma-separated addresses in the generated document.
  • Incident report submit sends the signed report to configured recipients and CC recipients.
  • Documents can be generated for CBS access requests and incident reports as PDF/DOC where the workflow allows.

12. Chat, Attachments, and Realtime Logic

  • Ticket chat access is calculated from requester, assignee, department membership, support roles, CBS approval participants, incident participants, and historical signers where applicable.
  • Chat can be locked by ticket state or privacy rules.
  • Message attachments are stored as ticket-linked attachment records and exposed only to users with ticket access.
  • Realtime consumers broadcast chat updates, notification changes, read state, and audio-call signaling to eligible users.

15. App Logic Change Checklist

  • For ticket form changes, update TicketForm, create_ticket.html, creation view validation, notification rules, and user guide.
  • For CBS workflow changes, update CBS form fields, description parsing/building, approval update logic, document generation, Central Operation actions, tests, and report export if fields change.
  • For incident report changes, update report model/form, sign-off formset, submit validation, download generation, correction behavior, and resolution blockers.
  • For permission changes, update visibility helpers, queue filters, chat access helpers, templates, and tests.
  • For email or notification changes, update the triggering view/helper, recipient logic, message body, and related tests.
