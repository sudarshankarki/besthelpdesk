BestSupport Application Workflow Documentation

Scope: application logic only.

1. Application Purpose

BestSupport is a Django helpdesk application for creating, assigning, approving, discussing, resolving, and closing support work. The main business flows are normal helpdesk tickets, CBS access requests, remote access requests, incident reports, ticket chat, audio-call signaling, technical documents, and portal announcements.

3. Request Routing Flow

  1. A browser request reaches Django.
  2. helpdesk/helpdesk/urls.py routes it to admin, accounts, tickets, health, or the root login redirect.
  3. Account routes are handled through accounts.urls; ticket routes are handled through tickets.urls.
  4. The matched view validates login state, permissions, form data, and model state.
  5. The view reads or updates models, sends notifications or email when needed, and renders a template or redirects.
  6. For live chat, audio-call signaling, and browser notifications, WebSocket requests are routed through tickets/routing.py to consumers in tickets/consumers.py.

5. Account Workflow

  1. A user signs in through /accounts/login/.
  2. login_view authenticates through the configured authentication backend.
  3. After login, users are redirected into the ticket/dashboard area.
  4. Signup and password reset routes are controlled by authentication feature flags.
  5. User department, branch, support role, Central Operation role, and signature image affect permissions throughout ticket, CBS, and incident workflows.

6. Normal Ticket Workflow

  1. User opens /tickets/new/.
  2. create_ticket builds TicketForm for the current user.
  3. The form validates request type, department, branch, notify email, assignment email, impact, urgency, CC emails, and attachments.
  4. On valid submit, a Ticket is created with a generated ticket ID and calculated priority.
  5. If an assignment email is supplied, the matching user becomes the assignee. If only notify email is supplied, that address receives notification but does not own the ticket.
  6. Department users can see department-routed tickets and may claim unassigned tickets when allowed.
  7. Support users work tickets through support queues and the ticket update page.
  8. Resolved tickets record resolution note, resolved user, resolved timestamp, and email the requester with a close link.
  9. Closed tickets become read-only for chat and cannot be reopened through the normal ticket panel.

7. Ticket Status Rules

Status AreaImportant Rule

ResolutionA ticket must be assigned before it can be resolved. Normally, only the assigned agent can mark it resolved.

Incident resolutionIncident tickets require required incident report conditions before resolution is accepted.
Approved CBS resolutionWhen an approved CBS access request is resolved, document sending, ticket update, and new chat messages are locked.

ticket_detail is the central page for a ticket. Its context decides which blocks and actions the user can see.

9. Chat and Call Workflow

  1. Ticket detail renders the Ticket Chat panel if the current user has chat access.
  2. can_access_ticket_chat decides chat membership.
  3. Normal ticket chat membership is based on requester, assignee, support/admin users, department membership, and private-chat settings.
  4. CBS access request chat membership is based on requester, assignee, current approval-chain users, users who already acted, Central Operation, IT support, and admins.
  5. Remote access approval requests that are not CBS access requests do not use ticket chat.
  6. Chat messages are sent over TicketChatConsumer, saved as TicketMessage, and broadcast to connected participants.
  7. Attachments are uploaded by the ticket attachment upload view and then announced in the chat stream.
  8. Audio calls use TicketCallConsumer only for signaling. Call permission follows the same chat access helper.
  9. Closed tickets disable chat and file upload. Approved CBS access requests also disable chat after the linked ticket is resolved.

10. CBS Access Request Workflow

  1. Head Office requests start at /tickets/cbs-access-request/.
  2. Branch requests start at /tickets/cbs-access-request/branch/.
  3. Both routes use the CBS access request view logic with office-specific fields.
  4. CBSAccessRequestForm validates requester details, access user, user groups, endorsement, recommender, second recommender for branch requests, approver, and attachments.
  5. The app creates a ticket and linked RemoteAccessApproval.
  6. The current reviewer can recommend or reject. Branch requests can require a second recommendation before final approval.
  7. Central Operation can adjust the signoff chain before final approval when allowed.
  8. When final approval is recorded, the approved CBS document is generated from saved request and approval data.
  9. The requester can assign the approved request to a concerned user and email the signed document while the ticket is still open.
  10. After final approval and ticket resolution, CBS document sending and ticket status editing are locked.

CBS Chat Membership

User TypeChat Access

11. Remote Access Request Workflow

  1. User opens /tickets/remote-access-request/.
  2. RemoteAccessRequestForm validates subject, details, recommender, and approver.
  3. The app creates a ticket and a linked RemoteAccessApproval.
  4. The approval record tracks pending recommendation, pending approval, approved, or rejected state.
  5. Reviewer decisions are handled by remote_access_approval_update.
  6. Remote access approval requests do not use the normal ticket chat flow.

12. Incident Report Workflow

  1. An incident ticket can have a linked IncidentReport.
  2. ticket_incident_report renders and processes the report form.
  3. Support users, the requester, and the incident commander can manage the report when allowed.
  4. The report tracks incident information, containment, recovery, lessons learned, action plan, notification data, and evidence notes.
  5. Evidence files are listed with view/download actions when the current user can access the incident report.
  6. Registered user and notified signoff users sign in sequence according to the saved signoff rows.
  7. Incident reports can be saved as draft, submitted, sent to reviewers/approvers, corrected, or locked depending on state.
  8. Incident ticket resolution is blocked until required report and signature conditions are complete.

Incident Report Access

User TypeAccess
Ticket participantCan view the incident report.
Incident commanderCan view and manage where allowed.
Registered userCan view/sign according to role.
Notified user or signoff userCan view/sign according to sequence.
Support/adminCan view and manage according to support permissions.

13. Technical Documents Workflow

  1. Users open /tickets/docs/ to see documents visible to them.
  2. Support users can upload documents through tech_docs_upload.
  3. Visibility can be public, branch-based, department-based, restricted to selected users, or support-only.
  4. View and download actions check document visibility before serving content.
  5. Supported spreadsheet documents can be previewed in a browser-friendly table view.

14. Portal Flash Announcements

  1. Support/admin users upload announcements through the portal flash upload page.
  2. Each announcement has title, message, image, visibility, and schedule fields.
  3. Active announcements are shown to users after login according to schedule and visibility rules.

Permission Change Rule

  1. Never rely only on hiding a button in a template.
  2. Enforce the same rule in the view handling the direct URL or POST.
  3. If WebSockets are involved, enforce the rule in the consumer access check too.
  4. If files are involved, enforce the rule on both view and download URLs.
  5. Add tests for both successful access and blocked access.

20. Detailed Workflow: Normal Ticket

  1. User opens the create ticket page.
  2. The form preloads user context such as available departments, branches, and support routing options.
  3. User selects request type, department/branch, impact, urgency, notify email, assignment email, CC emails, description, and optional attachments.
  4. The form validates email behavior. Assignment email must map to a real user and must not be a group mailbox. Notify email can be individual or shared mailbox according to rules.
  5. Priority is calculated from impact and urgency.
  6. The ticket is created with requester set to the current user.
  7. Assignment is applied if requested. Otherwise, department routing and support queues determine visibility.
  8. Notification email is sent to configured recipients.
  9. Requester lands on the ticket detail or list page and can continue in chat.
  10. Support users pick up work from support queues, claim if eligible, update status, and resolve/close according to rules.

21. Detailed Workflow: CBS Access Request

  1. Requester opens either Head Office or Branch CBS request form.
  2. The form captures user details, requested CBS user groups, request type, amendment reason where applicable, access user, signoff users, and supporting attachments.
  3. On submit, the app creates a ticket with request type cbs_access or cbs_access_branch.
  4. The app creates a linked RemoteAccessApproval with recommender, optional second recommender, and approver.
  5. The request detail appears inside the ticket detail page using saved ticket and approval data.
  6. The current reviewer receives the request and can recommend/reject.
  7. For branch requests, a second recommendation can be required before final approval.
  8. The final approver approves or rejects.
  9. Approved request displays signed approval information and allows allowed users to send/assign the approved document while the ticket remains active.
  10. CBS request chat is available to current chain users, historical signers, requester, assignee, Central Operation, support, and admins.
  11. If Central Operation changes the chain before a reviewer acts, the old reviewer loses chat access. If the old reviewer already acted, they keep access as a historical signer.
  12. Once approved and the linked ticket is resolved, approved document sending, ticket update, and new chat messages are locked.

22. Detailed Workflow: Incident Report

  1. Incident ticket is created or selected.
  2. Allowed user opens the incident report page from ticket detail.
  3. The report form captures incident timeline, service impact, branch impact, containment, recovery, root cause, lessons learned, recommendations, notification details, and action plan.
  4. Evidence files can be uploaded and later viewed/downloaded by users who can access the incident report.
  5. Registered user signature is copied from the user's profile signature when available.
  6. Notified signoff rows define ordered reviewers/signers.
  7. Signoff users can sign or reject according to sequence and role.
  8. Submit sends the report to configured recipients when required fields/signatures are complete.
  9. Incident ticket resolution checks report completion rules first.
  10. After finalization, normal editing is blocked.

26. Testing Guidance for New Developers

The most important tests live in tickets/tests.py and accounts/tests.py. When changing workflow behavior, add focused tests near the related test class.

Change TypeTest What
Permission changeAllowed user succeeds, blocked user fails, direct URL/POST path enforces the rule, and template does not show forbidden action.
Status transition changeValid transition succeeds, invalid transition is blocked, saved fields are correct, and user-facing message is shown.
CBS approval changeEach approval stage, final approval/rejection, signoff-chain changes, requester correction, and resolved-lock behavior.
Incident report changeDraft save, submit, signatures, signoff order, evidence access, resolution blockers, and finalized lock behavior.
Chat changeHTTP detail visibility, WebSocket access helper impact, attachment upload, delete, read-state, notification targets, and closed/read-only behavior.
Template action changeButton/link appears for allowed user and is absent for disallowed user; direct backend route must also be tested.

27. Safe Development Checklist

  1. Identify the URL and view first.
  2. Find the form and model involved.
  3. Find existing permission helpers before adding new checks.
  4. Update both UI visibility and server-side enforcement.
  5. For chat/call changes, confirm WebSocket consumer permissions still match HTTP permissions.
  6. For attachments/documents, confirm view and download URLs use the same intended access rule.
  7. For approval or incident changes, test both the current actor and a user who should not be allowed.
  8. Keep status-locking rules explicit; avoid changing resolved/closed behavior accidentally.
  9. Add or update focused tests before broader refactors.
  10. Do not mix unrelated UI, workflow, and data-model changes in one patch unless the feature truly needs all three.

28. How to Understand or Extend a Feature

  1. Start with helpdesk/helpdesk/urls.py to find the application route.
  2. Open the matching app urls.py to identify the view function.
  3. Read the view in views.py for permission checks, model queries, form validation, state changes, notifications, email, and template context.
  4. Read the form in forms.py for user-facing fields and validation rules.
  5. Read the model in models.py for stored fields, helper properties, status choices, and relationships.
  6. Open the rendered template to understand which actions are visible to each user.
  7. For real-time behavior, read asgi.py, tickets/routing.py, and tickets/consumers.py.
  8. For permission-sensitive changes, add tests around both the UI visibility and the direct URL/POST path.
